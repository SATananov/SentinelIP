# Phase 30: Perimeter evidence lifecycle close-out

Phase 29 selected indefinite growth of accepted perimeter evidence and derived
records as the next storage-lifecycle risk. Before Phase 30, perimeter classes
were `POLICY_UNDEFINED`; bounded batches, authentication, replay controls, and
idempotency limited individual ingestion requests but did not define a total
lifetime for accepted evidence.

Phase 30 establishes a manual lifecycle for unreferenced perimeter evidence
while preserving Incident Review evidence and complete dependency components.
It reduces eligible logical rows when an operator applies cleanup. It does not
hard-bound SentinelIP storage or memory.

## Decisions and implementation history

- **30A** mapped the event, detection, policy-correlation, host-correlation,
  and Incident Review reference graph.
- **30B** locked the 180-day server-receipt policy, whole-component deletion,
  indefinite Incident Review preservation, manual preview/apply, and the
  25-component apply cap.
- **30B-M** measured in-memory and TEMP-backed graph approaches. The selected
  implementation stages history-sized graph state in SQLite TEMP tables and
  uses bounded Python batches.
- **30B-I** advanced schema 45 to schema 46 with the two measured
  `primary_event_id` indexes described below.
- **30C** implemented the classifier, preview, apply, and operator UI.
- **30D-R** corrected Incident Review type handling: an unsupported nonempty
  textual evidence type is not inferred to be perimeter evidence and does not
  block perimeter cleanup. Empty, malformed, or non-text types remain
  fail-safe when a reference cannot be interpreted.

## Retention and timestamp contract

The fixed policy is:

- `PERIMETER_RETENTION_DAYS = 180`
- `PERIMETER_MAX_COMPONENTS_PER_APPLY = 25`
- age is measured from `perimeter_events.received_at`, generated by the
  SentinelIP server
- one UTC-aware evaluation time is captured per classification run
- `cutoff = evaluation_time - 180 elapsed days`
- a root is old enough when `received_at <= cutoff`; exact cutoff equality is
  eligible

`observed_at`, detection and correlation creation times, `first_seen`, and
`last_seen` do not control retention. Timestamps must be parseable ISO values
with an explicit timezone and are normalized to UTC. Future, malformed,
naive, invalidly encoded, and otherwise ambiguous timestamps are preserved. A
component is eligible only when every event root meets the cutoff. One newer
or ambiguous root preserves the whole component. Thus an event with an old
`observed_at` and a new server `received_at` is not immediately eligible.

## Components and graph inputs

The cleanup unit is the complete connected component of perimeter evidence.
The classifier includes these relationships:

- `perimeter_detections.primary_event_id` and every ID in
  `event_ids_json`
- `perimeter_policy_correlations.primary_event_id` and every ID in
  `event_ids_json`, `allowed_event_ids_json`, and `blocked_event_ids_json`
- `perimeter_host_correlations.event_id`

Primary IDs must agree with valid membership data. Malformed JSON, invalid or
duplicate IDs, a missing event, a primary/list contradiction, a site
inconsistency, or another unsafe graph anomaly blocks cleanup rather than
silently dropping an edge. Edges are traversed transitively: if one derived
row joins A to B and another joins B to C, A, B, and C form one component.
Components are identified deterministically by their minimum event ID. No
component is split across applies.

The graph is staged in connection-local SQLite TEMP tables. Source rows are
streamed in batches; the classifier does not fetch all history into Python or
build a Python union-find. It configures file-backed TEMP storage with a
connection-local 200-page TEMP cache. The current source batch is 128 rows;
membership JSON is byte-capped at 8 KiB and each decoded membership list is
capped at 256 IDs. `received_at` text is limited to 128 bytes for parsing;
larger values are preserved as malformed. Repeated runs recreate TEMP state, and
separate connections do not share it. TEMP storage still grows with the graph.
The resource statement is limited to this implementation shape: **history-sized
graph state is staged in SQLite TEMP structures; Python retains bounded working
batches/metadata in the implemented classifier.** Total process memory and TEMP
disk use have no hard bound.

## Incident Review preservation

Only these exact evidence types identify perimeter sources:

- `PERIMETER_DETECTION`
- `PERIMETER_POLICY_CORRELATION`
- `PERIMETER_HOST_CORRELATION`

A valid current `incident_review_evidence` reference protects the source row
and its whole component. Historical `EVIDENCE_ATTACHED` and
`EVIDENCE_DETACHED` entries do the same; detachment does not erase the fact that
evidence participated in a review. Malformed IDs, an exact perimeter reference
with a missing source, empty or malformed types on relevant reference rows,
and other unresolvable perimeter references block the classification run.
When ambiguity cannot be localized safely, preview reports
`cleanup_blocked = true` and apply deletes zero rows.

Unsupported nonempty textual evidence types, including `PERIMETER_UNKNOWN`,
are not matched by prefix, substring, suffix, case folding, or fuzzy rules.
They do not enter the perimeter graph or globally block its cleanup. A future
supported perimeter evidence class must be added as an exact type with explicit
source-resolution behavior.

## Preview and apply

Preview is non-destructive: it reads persistent rows and creates only TEMP
classification state. It reports the evaluation time, retention days, cutoff,
component and row counts, eligible/protected/ambiguous classifications,
oldest and newest eligible receipt times, largest eligible and protected
component sizes, apply cap, and cleanup-blocked state.

The preview retains standard inventory fields (`data_class`, `policy_state`,
`total_rows`, `expired_rows`, `eligible_rows`, `protected_by_review`,
`protected_by_dependency`, `policy_undefined`, `invalid_retention_rows`, and
`oldest_eligible_at`). Perimeter-specific fields include `evaluation_time`,
`retention_days`, `cutoff`, `max_components_per_apply`, `events_classified`,
`total_components`, `eligible_components`,
`age_eligible_components_before_global_block`, `protected_components`,
`newer_components`, `ambiguous_components`, `ambiguous_references`,
`graph_anomalies`, `unresolved_references`, `malformed_or_future_events`,
`malformed_skipped_rows`, `future_skipped_rows`, `eligible_events`,
`eligible_detections`, `eligible_policy_correlations`,
`eligible_host_correlations`, `protected_events`, `protected_detections`,
`protected_policy_correlations`, `protected_host_correlations`,
`oldest_eligible_received_at`, `newest_eligible_received_at`,
`largest_eligible_component_events`,
`largest_eligible_component_derived_rows`,
`largest_eligible_component_total_rows`,
`largest_protected_component_total_rows`, `cleanup_blocked`, and
`cleanup_block_reason`.

Apply is an explicit `POST /data-lifecycle/cleanup` action under the existing
`local_management` boundary. It requires `confirmed: true`; sensor credentials
cannot authorize it. Callers cannot choose the retention duration, cutoff,
component IDs, or apply limit. Apply begins `BEGIN IMMEDIATE` before rebuilding
the classifier and rechecking Incident Review protection. Preview IDs are not
used as deletion authority.

Eligible components are selected oldest-first by minimum normalized
`received_at`, then minimum event ID. At most 25 components are selected, not
25 rows. One large component counts as one component. Selected membership is
held in TEMP tables, not a giant Python ID list or generated parameter array.
Deletion order is:

1. `perimeter_host_correlations`
2. `perimeter_detections`
3. `perimeter_policy_correlations`
4. `perimeter_events`

The selected batch is all-or-nothing. A consistency or delete failure rolls
back the entire transaction. Returned `components_deleted`, `events_deleted`,
`detections_deleted`, `policy_correlations_deleted`, and
`host_correlations_deleted` counts are checked against actual delete rowcounts.
No eligible components is a successful no-op with zero counts. A blocked apply
deletes nothing and is not recorded as a successful cleanup audit event.
The response also returns `evaluation_time`, `cutoff`, `retention_days`,
`max_components_per_apply`, `cleanup_blocked`, `cleanup_block_reason`,
`eligible_components_before_apply`, and the largest selected component's
event, derived-row, and total-row counts.

Event ingestion persists the event batch before running the derived engines.
These are not one atomic event-plus-derived transaction. A newly persisted
event receives a fresh server `received_at`, so a partially derived fresh event
is not 180-day eligible. Cleanup classifies the committed graph it sees under
its writer reservation; this does not make the separate ingestion stages
atomic.

## Schema 46 indexes and evidence

Migration 46 adds exactly:

- `idx_perimeter_detections_primary_event` on
  `perimeter_detections(primary_event_id)`
- `idx_perimeter_policy_correlations_primary_event` on
  `perimeter_policy_correlations(primary_event_id)`

Phase 30B-M synthetic measurements found primary-event child lookups using
full-table scans and repeated scan cost while deleting roots with a large
derived-row population. After migration, the local SQLite query plans use
covering-index `SEARCH` operations on the respective `primary_event_id`
indexes. The indexes add persistent storage and insert/update maintenance; they
do not change foreign-key actions or evidence semantics. There is no
`perimeter_events(received_at)` index: existing measurements did not establish
that it was required, and the manual classifier’s receipt scan remains a
measurement candidate if future workloads show a problem. No permanent TEMP
graph tables, tombstone table, or schema 47 were added.

These are synthetic observations, not guarantees or service-level objectives.
TEMP page size was 4 KiB; page counts below are SQLite TEMP page counts, not a

| 1k singleton events | 0.039 s | 0.028 s | 0.07 MiB | 80 | 1 event |
| 10k singleton events | 0.271 s | 0.176 s | 0.05 MiB | 655 | 1 event |

these runs.

## Operator, audit, and storage contract

Cleanup is manual preview followed by explicit apply. There is no startup,
scheduled, background, sensor-triggered, or database-size-triggered cleanup.
A recent verified backup is strongly recommended but is not mechanically
required. Cleanup does not automatically run `VACUUM`; deletion reduces logical
rows and the database file may not shrink.

The lifecycle inventory reports `PERIMETER_EVIDENCE` under
`ACTIVE_RETENTION_POLICY`. This means a manual policy exists; it does not mean
cleanup runs automatically. Perimeter deletion counts are returned directly.
No migration was added to force this action into the existing typed audit event
that represents DNS and web cleanup.

The 180-day policy does **not** hard-bound database file size. Cleanup is
manual; incident-linked evidence can remain indefinitely; component size has
no hard maximum; ingestion continues; and SQLite file space may remain
allocated after deletes. Large components are not rejected or split, so an
operator may choose to apply a component whose deletion holds SQLite's writer
reservation longer.

After deletion, the existing uniqueness row is gone. A later sensor redelivery
of the same external identity may be accepted as a new row with a new server
`received_at` and a new retention interval. No tombstone or permanent
idempotency ledger is kept.

## Verification and remaining limits

Focused final verification covered migration/index checks, lifecycle graph and
timestamp tests, current and historical Incident Review references, malformed
and unsupported evidence types, preview/apply behavior, rollback, component
cap/order, redelivery, local-management authorization, lifecycle inventory,
Incident Review regressions, selected non-TestClient perimeter ingestion
checks, frontend lifecycle tests, ESLint, and Python compile/import.
The final run passed 139 lifecycle/index/data-lifecycle pytest cases, 53
Incident Review activity/search/trend cases, and 8 selected perimeter
ingestion cases (200 pytest cases total, with no overlap among those groups).
The Node lifecycle test and ESLint passed; Python compile/import passed.

The API-backed TestClient/AnyIO pre-router stall remains an environment
limitation; it is not reported as a passing suite. Some `api.main`-dependent
test modules cannot collect where `reportlab` is absent. Selected direct
service/database and authorization tests provide focused coverage without
claiming those blocked suites passed.

Other retained risks are manual restart/operation burden, indefinite protected
evidence, unbounded component size and TEMP storage, potentially long writer
reservations for large components, no hard cleanup latency or total-memory
bound, no `received_at` index, no physical file-shrink guarantee, and global
cleanup refusal when relevant malformed or unresolved evidence cannot be
interpreted safely. Phases 23–28 were not changed by Phase 30.
